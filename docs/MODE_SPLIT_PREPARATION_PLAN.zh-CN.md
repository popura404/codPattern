# codPattern 模式拆分准备阶段计划（中文译版）

> 状态：拟执行计划
> 范围：仅做拆分前准备；本计划不创建 Gradle 子项目、独立模组 JAR 或物理源码拆分
> 已确认平台：Minecraft Forge 1.20.1、Forge 47.4.0、Java 17
> 仓库快照核对日期：2026-07-25
> 边界复核：已于 2026-07-25 按实时源码与准备阶段约束补强；实现缺陷仍须遵守第 2 节的缺陷准入规则
> 文档性质：英文权威执行计划的完整中文译版
> 执行优先级：**项目实施以英文文档为准；如中英文存在差异，以英文文档为最终依据。**
> 英文权威文档：[MODE_SPLIT_PREPARATION_PLAN.md](MODE_SPLIT_PREPARATION_PLAN.md)

## 1. 目标

在暂不进行物理拆分的前提下，把当前合并在一起的 `codpattern` 代码整理到可以支持下列未来归属关系的状态：

```text
未来 codpattern 主模组
├─ 通用比赛 API 与可复用运行时
├─ 团队比赛共享运行时
├─ 冲锋模式（Frontline）
└─ 团队竞技模式（Team Deathmatch）

未来 Zombies 附属模组
├─ 僵尸模式规则与运行时
├─ 僵尸模式内容、资源、界面和工具
└─ 使用主模组公共 API 的适配器
```

必须遵守的依赖方向为：

```text
Zombies 附属 -> codpattern 主体 API/运行时
codpattern 主体 -X-> Zombies 具体实现
```

本计划会尽量把中立、可复用的实现抽入未来主体，同时把僵尸玩法规则留在未来附属中。准备工作的每个完成阶段都必须保证当前合并发行版仍然完整可用。

## 2. 权威要求与优先级

以下要求不可协商，并按优先级排序：

1. **任何现有模式功能都不得被删除、跳过、静默降级或替换成空实现。** 此要求同时适用于冲锋模式、团队竞技模式和僵尸模式。
2. 准备阶段必须兼容已有世界、地图、配置文件、玩家数据、注册 ID、命令、别名、翻译和网络行为。
3. 未来主体所属代码不得依赖僵尸模式的具体实现包。
4. 当某个实现能被至少两个模式使用且不需要引入模式专属规则，或它是契约与模式无关、明确中立的跨模式生命周期/基础设施原语时，应将其抽入主体通用层。
5. 模式专属规则必须留在所属模式中，不能把通用层变成大量 `if zombies` 条件的集合。
6. 本计划不创建独立 Gradle 模块、source set、模组元数据或 JAR；这些属于以后真正的物理拆分。
7. 重构不等于允许调整玩法平衡、重新设计 UI、重命名公共概念、改变网络包顺序或改写持久化格式。
8. 准备工作必须继续使用现有 Forge 1.20.1/Java 17 技术线：保持 Forge 事件总线、`DeferredRegister`/`RegistryObject`、`mods.toml` 和 `net.minecraftforge.*` 的侧别边界，不得引入仅 NeoForge 可用的 API 或 Java 21 假设。
9. 在行为刻画期间发现的既有缺陷，不得被静默冻结为预期行为，也不得混入结构重构。必须先记入缺陷台账，完成复现，定义预期契约，再把任何修复作为另行批准、边界狭窄的行为改动处理。

如果架构改进和功能保持发生冲突，优先保持功能，并通过兼容门面分阶段完成改进。

只有当某缺陷阻碍可靠刻画、使必要拆分边界无法工作，或会被本次抽取进一步固化时，才可进入准备阶段的执行顺序。在修改生产代码前，必须批准其复现方式、预期行为、兼容影响、修复边界和回归覆盖。通常应在受影响的通用抽取之前，以独立、可审查的改动落地缺陷修复。

## 3. 范围

### 3.1 本计划包含

- 明确并强制检查未来主体与附属代码的归属边界。
- 稳定现有比赛 API 和房间能力组合方式。
- 抽取中立的结果处理、准备状态、投票、名单同步、清理、实体归属、地图占用、玩家会话恢复、分阶段事务以及通用对象运行时实现。
- 为 Forge 注册、事件、网络、客户端展示、工具和调试建立扩展/贡献者边界。
- 通过共享团队比赛运行时和显式策略，收敛冲锋与团队竞技之间的重复实现。
- 调用方迁移期间保留原模式类作为兼容门面。
- 增加架构检查和行为基线，使后续物理拆分风险可控。
- 在不产出独立制品的前提下，演练仅主体逻辑的启动路径。
- 维护既有缺陷台账，并把缺陷分类为推迟处理、另行批准的前置修复或不在范围内。

### 3.2 本计划不包含

- 创建 `main` 与 `zombies` Gradle 子项目。
- 生成独立 Zombies JAR 或增加最终附属模组元数据。
- 决定最终附属模组 ID、发布版本规则或发行打包方式。
- 把网络包迁移到第二条网络通道。
- 改变地图/存档格式或强制执行数据迁移。
- 调整波次、武器、经济、Buff、队伍、得分、计时、出生规则或投票百分比。
- 把僵尸与 PVP 阶段机重写成一个万能状态机。
- 重新设计 HUD、编辑器界面、部署流程或资源。
- 未通过第 2 节缺陷准入规则的顺手缺陷修复。

## 5. 归属边界

### 5.1 未来主体所有

未来主体负责：

- 中立的模式定义、描述、房间标识、能力声明、快照、提示和结果契约。
- 公共模式端口和扩展接口。
- 房间注册表、运行时提供者注册表、持久化提供者注册表、编辑器结构注册表和客户端展示注册表。
- 可复用房间基础设施：准备状态、投票引擎、名单同步、清理编排、实体归属、地图租约、玩家会话标记/恢复、延迟动作、事务/回滚原语、对象注册/同步/分发、物品栏/工具生命周期原语以及通用事件路由。
- 冲锋和团队竞技共同使用的 PVP 团队比赛运行时。
- 冲锋与团队竞技的规则、适配器、UI、配置、持久化和资源。
- 已由多个模式使用，或完全以中立比赛模型定义的通用网络包。

### 5.2 未来 Zombies 附属所有

未来 Zombies 附属负责：

- 僵尸模式定义及其注册贡献。
- 波次定义、校验、导演、计时规则、出生组、僵尸生成和回收规则。
- 经济、点数、价格、购买、候选商品、Buff、护甲、复活和生命状态语义。
- 路障、窗户、电源开关、汽水机、强化机、弹药箱、护甲站、神秘箱和墙上武器。
- TaCZ 武器稀有度、强化、弹药规则、ItemStack 标签、武器过滤和伤害修正。
- 僵尸地图载荷、地图校验器、部署结构、部署工具、部署 GUI 和模式专属持久化适配器。
- 僵尸方块、物品、渲染器、HUD、标签、翻译、贴图、模型和其他资源。
- 僵尸专属客户端状态，以及没有中立含义的网络包。
- 将附属行为接入主体 API 的僵尸兼容门面。

### 5.3 暂时不得通用化的内容

即使下列内容表面上都有计时或状态逻辑，也继续保持模式专属：

- 僵尸波次状态机与 TDM 阶段状态机。
- 僵尸出生选择与 PVP 重生选择。
- 僵尸经济和任何看似通用的购买操作。
- 僵尸电源和机器启用逻辑。
- 僵尸武器稀有度、升级以及 TaCZ NBT/标签行为。
- 僵尸方块到对象的映射和载荷编解码。
- PVP 得分、队伍平衡、击杀信息、死亡镜头、热身和比赛记录；冲锋与团队竞技确实共享的部分只能通过 `TeamMatchRuntime` 复用。

这些区域中只抽取中立的事务、计时、注册、同步和回滚机制。

## 6. 依赖规则

准备工作必须先建立未来主体、Zombies 附属和临时装配层的文件/类暂定归属清单，再由该清单驱动自动化依赖检查，并满足以下规则：

1. `app.match.model`、`app.match.port` 和主体运行时包不得引用 `app.zombies`、`client.zombies`、`config.zombies`、僵尸地图类或僵尸内容类。
2. 团队比赛共享代码可以导入中立比赛层，但不得导入僵尸代码。
3. 冲锋和团队竞技可以导入团队比赛共享层和中立比赛层，但不得导入僵尸代码。
4. 僵尸代码可以导入主体公开比赛 API，以及仅依赖这些公共 API 的附属所有兼容门面/网关。兼容网关不得形成主体到 Zombies 的特权反向依赖，也不得绕过公共扩展边界。
5. 通用 Forge 事件处理器必须通过注册表/端口分发，不得直接判断 `isZombies(...)` 或实例化僵尸服务。
6. 客户端中立代码以及独立服务端可能加载的代码不得引用僵尸客户端类。
7. 仅在准备阶段，允许一个名称清晰的**合并发行版装配层**同时导入主体和 Zombies 启动类。它不属于未来主体，且不得包含玩法逻辑。
8. 架构检查应采用棘轮方式：先记录当前“未来主体到 Zombies”的例外并禁止新增，再把该白名单减少到零。唯一装配层由于明确不属于未来主体而单独跟踪；它是准备阶段唯一允许同时导入两侧启动类的位置。
9. 检查必须覆盖字节码/类型依赖和源码全限定引用，不能只检查 Java `import`。继承、方法/字段签名、注解、全限定类名、网络桥类型以及服务/资源描述文件都必须能被发现。
10. `BuiltInGameModes.ZOMBIES` 和 `isZombies(...)` 在准备阶段可以作为兼容身份 API 暂时保留，但未来主体的通用分发不得依赖它们。通用路由必须使用已注册定义/能力；该常量最终归属或弃用方案留到物理拆分决定。

当前 `@Mod` 入口可以在准备期临时充当合并发行版装配层，但未来主体初始化必须放在单独的核心启动类中，并且核心启动不得反向调用装配层。装配层只能是打包接线，未来替换时不得再次搬迁玩法逻辑。

暂定归属清单是阶段 0 的依赖棘轮输入，不是等到阶段 7 才产出的交付物；阶段 7 在全部迁移后将其定稿。包名看似通用但行为属于 Zombies 的文件必须显式分类，不能只按包名推断归属。

准备阶段建议的逻辑依赖形态：

```text
合并发行版装配层
├─ codpattern 主体启动
│  ├─ app.match API/运行时
│  ├─ app.teammatch PVP 共享运行时
│  ├─ 冲锋模式
│  └─ 团队竞技模式
└─ Zombies 启动
   ├─ app.zombies
   ├─ 僵尸 Forge/客户端/内容贡献
   └─ app.match API/运行时适配器
```

## 7. 兼容性契约

除非以后另行批准迁移方案，否则每个阶段都必须保持以下契约。

### 7.1 稳定的模式身份

- 规范游戏类型：`frontline`、`teamdeathmatch`、`zombies`。
- 现有别名：`cdptdm`、`cdptacticaltdm`。
- 已安装模式的现有顺序：安装 Zombies 贡献时依次为 `frontline`、`teamdeathmatch`、`zombies`。
- 现有房间键编码：经过 trim 的 `gameType + "|" + mapName`，包括当前分隔符和大小写行为。抽取内部索引时不得静默把公共房间/地图 ID 转为小写。
- 保持公共房间身份与内部占用身份之间的现有区别：`RoomId` 保存经过 trim、但保留大小写的地图名；当前 Zombies 占用键则会 trim 并转为小写。
- 准备阶段不得删除临时兼容身份 `BuiltInGameModes.ZOMBIES`，即使通用分发已停止使用它。
- 现有模式显示、房间标题、命令和翻译键。

### 7.2 稳定的注册与资源身份

所有现有注册名和命名空间保持不变，包括但不限于：

- `codpattern:zombies_power_switch`
- `codpattern:zombies_player_barrier`
- `codpattern:zombies_red_player_barrier`
- `codpattern:zombies_weapon_wall_box`
- `codpattern:zombies_ammo_box`
- `codpattern:zombies_armor_station_box`
- `codpattern:zombies_soda_machine_box`
- `codpattern:zombies_ultimate_machine_box`
- `codpattern:zombies_deploy_tool`

以后改变注册归属时，不得创建替代 ID 或重复注册。

### 7.3 稳定的持久化与玩家数据

- 现有地图保存位置和编解码器。
- 僵尸规则根目录：`serverconfig/codpattern/zombies_rules`。
- 僵尸武器过滤文件名：`zombies_weapon_filter.json`。
- 玩家 NBT 根：`codpattern.zombies`。
- 实体归属标签：`codpattern_room_key`。
- 现有 `codpattern.zombies.*` 武器和运行时 ItemStack 标签。
- 所有语言文件中的现有翻译键和占位符数量。

新的中立存储 API 必须允许适配器继续读写这些完全相同的旧键。

### 7.4 准备阶段稳定的网络行为

- 主通道：`codpattern:main`。
- 当前协议字符串：`10`。
- 当前网络包注册顺序和判别 ID 序列。
- 当前方向、编码、解码、处理线程和接收者语义。
- 通用运行时/对象/房间包继续使用当前通道。

可以把僵尸专属注册器隔离为贡献者，但准备阶段必须在现有注册序列中的相同位置调用它。网络注册必须有确定性的“包类到判别 ID”清单。如果仅主体演练省略 Zombies 贡献，则必须显式保留旧槽位，或者该演练不得注册实际网络通道，避免后续主体网络包 ID 意外前移。第二条附属通道推迟到物理拆分，并且必须另写兼容方案。

### 7.5 稳定的行为

冲锋与团队竞技在适用时必须保持：

- 地图创建、加载、保存、别名和编辑器数据。
- 房间发现、加入、离开、观察者、队伍选择和队伍平衡。
- 准备状态、开始投票、结束投票、投票阈值、超时和成员退出行为。
- 热身、移动锁定、出生/重生选择、初始装备、计分、击杀信息、死亡镜头、战斗标记、HUD、比赛结束、结束传送和比赛记录。

僵尸模式必须保持：

- 地图创建/加载/保存、校验、部署流程和全部地图对象类型。
- 大厅加入/离开、准备状态、开始投票、当前投票失败原因以及不支持结束投票的行为。
- 启动预检、地图占用、出生分配、传送、初始装备、回滚和失败报告。
- 波次/间歇生命周期、出生组、僵尸计数、实体清理、崩溃恢复和房间清理。
- 经济、点数、武器、弹药、护甲、Buff、复活/死亡、电源、路障、机器和购买。
- 运行时/对象同步、HUD、提示、世界标签、战斗标记、重连恢复、赛后传送和待处理恢复行为。

“能够编译”不能证明功能保持。每个适用项目都必须由测试、静态契约检查、GameTest 或记录清楚的人工验证结果覆盖。

### 7.6 稳定的 Forge 加载器与生命周期行为

- 保持 Forge 1.20.1、Java 17、`META-INF/mods.toml`、`net.minecraftforge.*`、`DeferredRegister` 和 `RegistryObject` 约定。
- 每个被移动处理器的事件总线（`MOD` 或 `FORGE`）、物理侧、事件优先级、取消处理行为和注册时机必须保持不变。
- 方块/物品 `DeferredRegister` 和创造栏监听器必须在模组构造阶段、注册事件触发前接入；common setup 对这些注册已经太晚。
- `SimpleChannel` 网络包继续在现有 common-setup 路径中以确定顺序注册。
- Overlay、渲染器、界面和客户端网络桥只允许在 `Dist.CLIENT` 保护的客户端生命周期路径安装。
- 合并发行版安装 Zombies 时，缺少必需的 Zombies 贡献必须明确失败，不能静默降级。只有仅主体演练或该物理侧不适用时，贡献缺席才是有效状态。

## 9. 必须实施的改动方向

### 9.1 稳定 `ModeRoomHandle` 与能力组合

当前问题：`ModeRoomHandle` 使用很长的位置构造参数，其中有 15 个可选端口，并存在多个重载；继续加能力会提高调用错误风险。

方向：

- 增加 Builder 或不可变能力集合，把 `roomId`、摘要端口和生命周期端口设为必需项。
- 使用 `withReady(...)`、`withVote(...)`、`withRoster(...)` 等具名方法替代位置可选参数。
- 只为当前确实存在直接端口映射的能力定义显式 capability-to-port 关系，并先以诊断/棘轮方式校验，不能直接做全量相等判断。当前合法定义还会声明动态复活、结束传送、回合开始出生、战绩和模式专用地图能力，而这些能力并非每项都对应一个独立 `ModeRoomHandle` 端口；校验不得误拒绝现有合法 handle，也不得虚构一一映射。
- 旧构造器作为弃用兼容路径保留，直到所有房间工厂迁移完成。
- 此步骤不改变运行时行为或端口语义。

### 9.2 抽取中立结果与错误契约

当前候选：`ZombiesServiceResult`、`ZombiesErrorCode` 和 `ZombiesDeployServiceResult`。

方向：

- 在主体层增加中立 `ModeOperationResult<T>` 和值语义 `ModeErrorCode`。
- 把这些结果/错误类型视为公共 API 契约，而不是仅供运行时内部使用的实现类。
- 模式专属常量、消息键和展示映射继续留在 Zombies。
- 展示消息键必须与值语义错误码独立保存。`ZombiesDeployServiceResult` 可能让同一个成功/错误码对应不同消息键，因此从错误码反推消息键无法做到无损适配。
- 保留结构化具名参数、按顺序传给翻译的参数、可选返回值和仅用于日志的诊断文本。适配器必须同时完整覆盖 `ZombiesServiceResult` 与 `ZombiesDeployServiceResult`，不得改变占位参数的顺序或数量。
- 保留弃用的 Zombies 门面类型或转换帮助方法，以便增量迁移。
- 不进行一次性全局替换。

### 9.3 抽取准备状态和投票引擎

当前候选：`ZombiesReadyService`、`ZombiesStartVoteService`、`app/tdm/service/VoteService` 和 `CodTdmVoteCoordinator`。

方向：

- 增加可注入阶段、成员/准入、初始化、移除和变更通知策略的 `DefaultReadyStateService`。
- 保持当前差异：Zombies 在等待阶段可把传入 UUID 记录为已知玩家，而 TDM 会拒绝不属于当前房间成员的准备状态修改。
- 分开保持操作结果与通知语义。`ZombiesReadyService.setPlayerReady(...)` 的返回值表示操作是否被接受，而不是保存值是否变化：只有实际变化时才把房间状态标脏，但当前 Zombies 房间门面仍会在每次被接受的 set 操作后发送全量名单快照，包括重复设置同一值；当前 TDM 路径也会在每次被接受的 set 操作后执行同步动作。不得把“接受”和“变化”压成同一个布尔含义。
- 保持初始化/重置副作用：Zombies 的准备状态初始化会强制写为 false 并把房间标脏，Zombies clear 也会标脏；当前 TDM 协调器初始化/清空准备状态映射时不会直接调用同步动作，而是依赖外围生命周期调用。
- 增加可注入投票类型、资格、前置条件、阈值、超时、回调和成员退出策略的 `RoomVoteEngine`。
- 保留下列重要语义差异：
  - Zombies：快照成员退出时，本次投票失败。
  - TDM：退出成员从投票中移除，并重新计算所需阈值与投票结果。
- 保持 Zombies 只支持开始投票，TDM 支持开始/结束投票。
- 翻译消息和模式专属失败措辞留在中立引擎之外。
- 旧服务类作为薄门面保留，直到调用方和测试迁移完成。

### 9.4 抽取名单同步

当前候选：`CodTdmClientSyncCoordinator` 与 `ZombiesRoomHandleFactory` 中手工发送全量快照的代码。

方向：

- 增加 `RoomRosterSyncCoordinator`，负责版本、全量快照、增量、新接收者初始化、重同步和周期校准。
- 注入名单构造、排序、接收者选择、时钟/周期以及网络包发布。
- 保持当前网络包类型和版本语义。
- 必须区分 Zombies 的成员投影：已占用幸存者 ID 决定房间摘要人数与容量；在线玩家决定实时名单载荷和实时广播/重同步接收者；在线幸存者 ID 决定开局投票快照。通用协调器不能从同一个集合推导这三种视图。
- 实时名单投递、重同步授权与房间预览回复必须使用彼此独立的接收者策略。Zombies 实时全量快照广播给在线幸存者，显式重同步要求请求者属于幸存者，而 `RoomPreviewRosterPacket` 即使面对非房间成员请求者也可以定向回复；其预览载荷仍使用在线幸存者视图。TDM 同样允许独立于“已加入玩家/观察者”实时接收者集合的请求定向预览。
- 整个准备阶段都必须保持 Zombies 当前的全量快照行为。即使已有等价测试，后续改用增量也属于本计划之外、需另行批准的行为/优化改动。
- 保持 TDM 当前真实周期语义：从地图 Tick 路径发现的待发增量可以立即刷新，150 ms 阈值只限制非 Tick 的同步调用；除非另行测量并批准行为改动，否则保持 7000 ms 全量校准行为。

### 9.5 收敛清理、实体归属和地图占用

当前候选：`ZombiesCleanupService`、`ZombiesCleanupParticipant`、`ZombiesMapOccupancyService`、`ModeEntityOwnershipRegistry` 和 `ModeRoomTickEventHandler`。

方向：

- 抽取 `RoomCleanupCoordinator` 与有序、幂等的清理参与者。
- 通过显式策略完整保持当前清理顺序：before hook、实体清理、有序且失败即停止的参与者、运行时清空 hook、占用释放、after hook。当前参与者失败发生在实体清理之后、运行时清空与占用释放之前。
- 区分成功的幂等清理与有意保留的失败状态。参与者失败后占用仍被保留时，除非重试/恢复契约规定此时本应释放，否则不得把它误判为泄漏。
- 把占用机制通用化为按规范游戏类型及由适配器提供的归一化地图键索引的 `ModeMapLeaseRegistry`，并返回不透明的租约令牌/代际号。Zombies 适配器必须保持现有 trim/小写占用键，而中立注册表不得感知这一模式专属归一化规则。正常释放必须幂等，且必须拒绝旧房间生命周期留下的过期令牌。
- 在把 Zombies 迁移到令牌/代次租约前，必须先刻画当前重复获取、旧释放、强制失效和恢复行为；任何有意改变的语义都要通过第 2 节缺陷准入门禁。不能仅因令牌保护在架构上更合理，就把它视为行为中立。
- 保留服务器启动/停止、残留标签实体清理、管理强制失效以及完整临时注册表清空等显式恢复操作。迁移前必须定义重复获取与强制失效后重新获取的行为。
- 让 `ModeEntityOwnershipRegistry` 成为实体到房间归属的事实来源。
- 增加中立的实体丢失校准回调，替代通用处理器直接导入 `ZombiesActiveMobCounter`。
- 解决当前僵尸活动实体 ID 在以下三处重复追踪的问题：
  - `ModeEntityOwnershipRegistry`
  - `ZombiesActiveMobCounter`
  - `ZombiesWaveRuntimeState.activeZombieEntityIds`
- 僵尸波次预算/完成语义继续留在 Zombies；归属与校准通过 Zombies 适配器从主体归属表派生。
- 保持 `codpattern_room_key` 和清理幂等性。

### 9.6 抽取玩家会话与恢复原语

当前候选：`ZombiesPlayerRuntimeMarkerService`、`ZombiesReconnectRecoveryService`、`ZombiesPostGameTeleportService`、`ZombiesConnectionStateService`、`CodTdmTeamMembershipCoordinator` 和 `CodTdmDeferredLeaveRegistry`。

方向：

- 增加支持可插拔持久化键的中立玩家-房间会话标记契约。
- 增加宽限期/延迟离开原语以及待处理玩家动作或传送队列。
- 增加由模式适配器驱动的 `PlayerRecoveryCoordinator`，模式适配器负责活动房间查询、恢复方式、回退传送、物品栏处理和清理策略。
- 用恢复贡献者替代全局登录处理器里的僵尸专属逻辑。
- 通过 Zombies 存储适配器保留原 NBT 根和当前回退行为。
- 不强制 PVP 与 Zombies 使用相同重连策略。

### 9.7 抽取分阶段事务与回滚机制

当前候选：`ZombiesStartupFlow`。

方向：

- 只抽取有序阶段执行、参与者调用、回滚栈、回滚报告和失败传递机制。
- 僵尸预检、地图租约获取、出生分配、传送、初始装备准备/应用、阶段切换和僵尸错误码继续留在 Zombies。
- 回滚动作必须具名，尽量幂等，并按反向顺序验证。
- 不创建同时认识 Zombies 和 PVP 分支的万能“比赛启动”类。

### 9.8 抽取通用对象运行时机制

当前候选：`ModeObjectState`、`ModeInteractableObjectPort`、`ModeObjectStateSyncPacket`、`ZombiesObjectStateStore` 和 `ZombiesObjectInteractionService`。

方向：

- 主体可负责对象注册、稳定对象 ID、空间查询/索引、版本追踪、每 Tick 交互去重、旧版本拒绝、状态发布和处理器分发。
- 对象载荷对通用运行时保持不透明。
- Zombies 负责对象类型、价格、购买规则、电源要求、TaCZ 武器处理、方块映射、消息和载荷编解码。
- 移动任何中立组件前，先按职责拆开两个大型 Zombies 类。
- 不把完整 Zombies 状态仓库或交互服务整体移入主体。

### 9.9 增加工具、HUD、客户端与调试贡献边界

当前候选包括 `FPSMEvents`、`FPSMItemRegister`、`ClientModEvents`、`ClientPacketBridgeInstaller`、`FpsmClientPacketBridge`、`FpsmClientPacketHandler`、`ModePreviewPanel`、`TdmVanillaHudSuppressor` 和 `ModeDebugCommand`。

方向：

- 增加手持工具预览生命周期注册表，使全局 FPSMatch 事件不再点名僵尸部署工具。
- 增加 Overlay/HUD 策略贡献者，使 TDM HUD 屏蔽代码不再导入 `ClientZombiesState`。
- 客户端展示应提供完整的带命名空间资源标识（`ResourceLocation` 或等价的 namespace/path 值对象），不再由 `ModePreviewPanel` 补上主体模组命名空间。
- 把共享 FPSM 客户端网络桥/处理器中带 Zombies 类型的方法替换为附属所有的处理贡献，或中立的界面打开分发器，使未来主体方法签名不依赖 Zombies 网络包或界面类。
- 调试命令通过模式键查询调试快照贡献者，不再直接分支到 Zombies。
- 将通用 FPSM 工具与 Zombies 工具分开归属，同时保持注册 ID 和创造栏可见性。
- 所有仅客户端贡献实现不得进入独立服务端类加载路径。

### 9.10 隔离 Forge 装配、事件、注册和网络钩子

应建立一组小而专注的扩展契约，而不是一个权限无限的“万能启动器”。必须覆盖：

- 模式定义/运行时/持久化/编辑器注册。
- Forge 方块/物品注册与创造栏贡献。
- 通用玩法事件贡献。
- 登录/恢复贡献。
- 网络包注册贡献。
- 客户端网络桥、Overlay、渲染器和界面贡献。
- 工具预览和调试贡献。

准备阶段要求：

- 把剩余直接 Zombies 引用集中到 `ZombiesBootstrap` 和一个明确可丢弃的合并发行版装配层。
- 未来主体初始化应放在独立的核心启动器中。如果当前 `@Mod` 类暂时承担合并发行版装配层，它只能包含有序启动接线。
- 保持每类贡献原有的生命周期槽位：
  - 模组构造/模组事件总线：模式定义、`DeferredRegister` 挂接和创造栏监听器；
  - common setup：确定性网络包注册；
  - client setup 与客户端 MOD 事件：客户端网络桥和 Overlay；
  - Forge 事件总线：玩法、登录、Tick、渲染和交互处理器。
- 盘点由 Zombies 所有的 `@Mod.EventBusSubscriber` 类；移到 `ZombiesBootstrap` 背后时，必须保持其事件总线、`Dist`、优先级和取消语义。
- 保证处理器与监听器恰好注册一次；自动订阅的类不得在等价处理器又由贡献者手工注册时继续生效。
- 网络包必须严格保持当前注册序列，使用显式确定性排序；演练中某个可选贡献不存在时，仍要保留其旧判别号槽位。
- 不通过反射或静默可选加载来隐藏初始化错误。
- 扩展 API 应能由未来附属入口直接调用。

### 9.11 建立共享 `TeamMatchRuntime`

当前候选：`CodTdmMap`、`CodTacticalTdmMap`、TDM 服务、战术端口、持久化提供者和编辑器结构。

方向：

- 对冲锋和团队竞技真正共享的行为引入 `TeamMatchRuntime`。
- 注入 `TeamMatchPolicy` 或更小的策略，覆盖：
  - 规范游戏类型和别名；
  - 重生选择；
  - 动态重生支持；
  - 配置访问；
  - 地图持久化/编辑器特性；
  - 展示键；
  - 比赛记录路径和模式专属标签。
- 增量替换大段委托包装。
- 保持冲锋当前规则和团队竞技当前动态重生行为。
- 此工作应在中立准备/投票/名单/生命周期原语稳定后进行，避免 PVP 收敛时吸收僵尸假设。

## 11. 分阶段执行计划

每个阶段必须能够独立审查、构建和回退。当前阶段退出条件未通过前，不得开始下一阶段。

### 阶段 0——冻结兼容基线

任务：

- 在启用依赖棘轮前，先建立未来主体、Zombies 附属和临时装配层的文件/类暂定归属清单；按职责而不是只按包名分类行为。
- 把全部公共模式 ID、已安装模式顺序、别名、房间键编码/大小写行为、注册 ID、命令、配置/存档路径、NBT 键、翻译键、网络包“类→判别 ID/方向”顺序、事件总线元数据和协议值记录到可机器检查的兼容清单。
- 为当前注册到 `codpattern:main` 的每个 codPattern 网络包保存黄金编解码夹具，包括代表性编码字节、解码往返、网络包类到判别 ID 的映射、注册顺序和方向；同时记录有意不注册的本地类网络包类型，避免把它误判为夹具遗漏。翻译快照不仅记录键是否存在，还要记录占位符数量和有序参数。
- 保存有代表性的现有地图/配置载荷、玩家 NBT 和 Zombies `ItemStack` 标签作为读写往返夹具。清理夹具中的隐私或环境信息时，不得顺带归一化旧数据的大小写、顺序、未知字段或精确键名。
- 增加带当前例外列表的依赖棘轮测试；使用字节码/类型分析或等价检查，同时捕获完全限定名引用和带 Zombies 类型的签名。
- 通过一个或多个显式 Gradle 任务，为 common/PVP 契约增加可实际执行的聚合验证覆盖。维护静态契约测试迁移台账：每项测试必须被聚合任务调用、提升为 JUnit/GameTest，或明确记录为待迁移；仅编译成功不算执行。
- 修改 PVP 共享代码前先增加 PVP 基线测试。
- 记录冲锋、团队竞技和 Zombies 的行为矩阵。
- 把 `d363fbe` 之后的 Zombies 成员投影和清理顺序写入可执行基线：区分占用中的重连槽位与仅在线的名单/投票成员；区分实时广播/重同步接收者与请求定向的房间预览接收者；区分已接受的准备操作与准备状态实际变化；先捕获待处理的赛后恢复，再释放离线槽位；并保证离线槽位释放早于运行时/玩家状态清除。
- 建立既有缺陷台账，记录复现状态、预期契约、兼容影响、处置结论、负责人和必需回归覆盖。行为刻画快照必须标明已知失败，不能把失败转换成预期行为。
- 确认当前构建、自定义兼容套件和 GameTest 状态。

PVP 基线至少覆盖：

- 准备状态阶段限制。
- 开始/结束投票阈值、超时和退出行为。
- 名单全量、增量、版本、新接收者初始化和重同步。

退出条件：

- 暂定归属清单已经驱动依赖基线，每个归属含糊的共享文件都有明确的暂定所有者。
- 兼容、编解码、翻译占位符、持久化、NBT、ItemStack、事件和注册快照均可审查且可复现。
- common/PVP 聚合任务会实际执行其声明的测试，静态契约迁移台账中没有未分类测试。

- 基线产物已经形成可审查的仓库改动；本文档本身不授权 Git commit、push 或发布操作。
- 现有功能可以重复验证。
- 未改变生产行为。

### 阶段 2——抽取准备、投票和名单运行时

| 代理 F——Forge 集成 | 启动、事件、网络、注册、工具、客户端贡献 | 装配隔离、符合生命周期的接线、订阅者迁移、确定性网络包槽位 | 网络包顺序/ID、注册 ID、事件总线/侧/优先级、客户端/服务端边界 |

| 代理 H——验证 | 独立测试、静态契约、GameTest、人工矩阵 | 阶段审计和无回归签字 | 除狭窄批准的测试钩子外不得改生产行为 |

### 12.1 文件归属与冲突规则

- 每个阶段开始前，主代理为所有共享文件指定唯一负责人。
- `CodPattern.java`、`ModNetworkChannel.java`、`GameModeDefinition.java`、`ModeRoomHandle.java`、全局 Forge 事件处理器和共享网络包注册器属于串行集成文件，同一时间只能由一个代理编辑。
- 每项用通用实现替换 Zombies 服务的改动都必须由代理 G 审查。
- 影响队伍或 PVP 语义的公共 API 改动必须由代理 E 审查。
- 代理 H 应依据行为契约和依赖规则审查，不能只依据作者对实现的说明。
- 子代理按工作流交付小型审查单元；只有在另行授权版本控制操作时才使用 commit。不得把包移动、行为改变和网络/注册改变合并在同一审查单元中。
- 如果所需抽象会改变另一代理的契约，应先暂停并更新共享契约，不能并行创建近似重复 API。

### 12.2 建议合并顺序

1. 主代理与代理 H 完成阶段 0 验证基线。
2. 合并代理 A 的核心 API 改动。
3. 合并代理 B 的大厅/同步改动。
4. 合并代理 C 的生命周期/会话改动。
5. 合并代理 D 的对象运行时改动。
6. 合并代理 F 的装配与 Forge 钩子隔离，并同步合并代理 G 的适配器。
7. 合并代理 E 的团队比赛收敛。
8. 由代理 H 完成独立全量审计和阶段 7 演练。

代理 G 应贯穿第 2～6 步参与，而不是最后才集中适配，确保兼容门面不会落后于抽取实现。

### 13.3 架构检查

出现下列情况时验证必须失败：

- 未来主体包或类型对 Zombies 具体实现存在任何依赖，即使源码中没有 Java import。
- 即使没有 `import` 行，未来主体类型仍通过完全限定名引用、继承、注解、字段/方法签名、网络桥类型、服务描述符或资源元数据依赖 Zombies。
- 本应使用端口/贡献者的通用处理器直接按 Zombies 模式身份分支。
- 主体模型包含 Zombies 载荷键或错误常量。
- 通用运行时要求 Zombies 方块、物品、地图、服务、客户端状态或渲染器类。
- 独立服务端会加载的类导入仅客户端贡献者。
- 准备阶段新增网络包导致既有判别 ID 改变。
- 演练时省略某个贡献，导致后续网络包 ID 填入其旧槽位，而不是保留这些槽位。
- 注册 ID、翻译键集合、配置路径、NBT 键、模式顺序、房间键编码规则或别名消失。
- 网络包编解码在未获批准时改变既有字节/方向/判别 ID，翻译占位符丢失或参数换序，或者旧地图/配置/NBT/ItemStack 夹具不能按其既定保留规则完成往返。
- 移动后的 Forge 处理器改变 MOD/FORGE 总线、物理侧、优先级、取消行为或注册时机。
- 某个 Forge 处理器/监听器在合并发行版中注册零次或多于一次。
- 静态契约测试只被编译，却既未由聚合任务执行，也未在迁移台账中分类。
- 模拟外部/新模式贡献者必须增加 Zombies 分支或修改通用路由才能被调用。

## 15. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| 把 Zombies 行为过度通用化到主体 | 至少要求两个使用方或明确中立生命周期关注点；禁止通用代码出现 Zombies 常量/分支。 |
| 投票语义漂移 | 注入成员退出和投票类型策略；分别用对应的通用引擎运行 TDM 与 Zombies 契约测试。 |
| 网络包判别 ID 漂移 | 快照记录注册序列；隔离注册器时不改变调用顺序。 |
| 可选贡献者使后续网络包 ID 位移 | 使用显式“网络包类→ID”清单，并在仅主体演练中保留旧槽位。 |
| 注册重复或内容缺失 | 快照全部注册 ID；每个审查单元中每个 ID 都只能有一个注册所有者。 |
| 静态注册表污染导致仅主体演练假通过 | 在全新 JVM/类加载器中运行演练，或为每个静态模式注册表提供范围严格受限的仅测试重置钩子。 |
| 仅测试注册表重置掩盖生产类路径耦合 | 重置只用于快速迭代；最终签字必须在附属实现类缺席的全新 JVM/类加载器中运行。 |
| 存档/NBT 不兼容 | 在完全相同旧路径/键之上使用存储适配器；用已有夹具做往返测试。 |
| API 层测试未发现编解码或翻译消息漂移 | 快照代表性网络包字节、方向、判别 ID、占位符数量和有序翻译参数。 |

| 独立服务端加载客户端类崩溃 | 分离客户端贡献接口，并在集成阶段后测试服务端启动。 |
| 事件订阅者搬迁后行为改变 | 快照并保持事件总线、侧、优先级、取消和生命周期时机。 |
| 隐式订阅和手工注册同时存在，导致行为执行两次 | 盘点订阅者类，并在贡献者迁移后断言恰好注册一次。 |

## 18. 建议的初始门禁执行顺序

初始实施范围应保持有界，且不得包含未经批准的行为修复。它由三轮可独立审查的工作组成，而不是一个跨阶段合并单元。每轮都必须通过本阶段退出门，并由独立代理立即复核后，才能进入下一轮：
